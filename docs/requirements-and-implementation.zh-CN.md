# Syncodex 需求说明与实现方案

## 1. 项目定位

Syncodex 是一个运行在 Windows 本机的官方 Codex 同步桥接工具。

它的目标不是替代官方 Codex，而是补足官方桌面端在这些场景下的体验：

- 手机查看和继续线程
- 浏览器里更清晰地查看任务过程
- 在不破坏官方数据源的前提下做同步、排队、提醒和自动化

核心原则：

1. 官方 Codex 仍然是唯一事实源
2. Syncodex 优先读官方数据，不直接改官方 SQLite
3. Syncodex 的发送链路优先走官方桌面 IPC
4. 手机端体验可以增强，但不能牺牲同步准确性

## 2. 主要需求

### 2.1 基础同步

需要做到：

- 读取官方 Codex 本地线程列表
- 读取 thread 标题、状态、模型、推理档位
- 读取 rollout 事件并还原消息时间线
- 在浏览器和手机端展示官方线程内容

实现方案：

- 读取 `%USERPROFILE%\.codex\state_5.sqlite`
- 读取 `%USERPROFILE%\.codex\session_index.jsonl`
- 读取 `%USERPROFILE%\.codex\sessions\...\rollout-*.jsonl`
- 后端整理成前端可消费的 session / timeline 数据结构

### 2.2 发送消息到官方 Codex

需要做到：

- 从 Syncodex 页面继续官方线程
- 不靠直接写 SQLite 或伪造 rollout
- 保持官方桌面端立即可见

实现方案：

- 默认走官方桌面 IPC：

```text
\\.\pipe\codex-ipc
-> thread-follower-start-turn
```

- 当目标线程当前没有 follower client 时，只对 `no-client-found` 这类安全失败做 `app-server` fallback
- 避免“一失败就 fallback”造成双发

### 2.3 手机端访问

需要做到：

- 手机和电脑不在同一局域网时仍能访问
- 不暴露本机裸端口
- 尽量降低用户配置成本

实现方案：

- 托盘菜单启动手机访问
- 使用 `cloudflared.exe` 建立临时 Cloudflare tunnel
- 公网只进入带 token 的本机代理
- 本地 bridge 仍监听 `127.0.0.1`

链路：

```text
手机浏览器
  -> 临时公网隧道
  -> token 代理
  -> 127.0.0.1:8765
```

### 2.4 手机端输入与队列

需要做到：

- 官方 Codex 忙碌时，手机输入不要丢
- 官方队列与 Syncodex 本地队列要同时可见
- 队列优先级清楚
- 队列项支持编辑、删除、移到最前

实现方案：

- 保留官方队列只读展示
- 增加 Syncodex 本地队列
- 队列优先级：

```text
官方 Codex 队列 > Syncodex 自动下一步队列 > Syncodex 本地普通队列
```

- 本地队列状态落到浏览器本地存储
- 增加跨标签页 flush 锁，防止多标签重复发送

### 2.5 完成后动作

需要做到：

- 一轮完成后，用户能快速做后续动作
- 支持自动朗读
- 支持自动继续
- 自动继续不能依赖脆弱的瞬时事件时序

实现方案：

- 顶部 `选项` 面板提供完成后动作相关设置
- 自动继续改为 Syncodex 本地队列模型，而不是 completion notice 直接发送
- 自动继续提示词固定为：

```text
自动下一步
```

- 自动继续保护条件：
  - 达到次数上限停止
  - 出错停止
  - 等待确认停止
  - 计划已完成停止

### 2.6 按线程保存自动化偏好

需要做到：

- 不同线程可独立配置自动朗读和自动继续
- 当前线程的设置不影响其他线程

实现方案：

- 保留全局默认值：`completionActions.prefs`
- 把线程覆盖值保存到：

```text
completionActions.threadRuns[sessionId].prefs
```

- 当前线程优先读自己的 `prefs`
- 线程级设置覆盖以下项目：
  - 自动朗读
  - 自动继续
  - 自动继续最大次数

### 2.7 自动朗读与音频播放

需要做到：

- 手机端完成后自动播报
- 不依赖手机浏览器是否稳定支持 `speechSynthesis`
- 朗读内容要短，能抓住核心信息

实现方案：

- 后端优先使用 Windows SAPI 生成音频
- 手机端通过 `<audio>` 播放 wav
- TTS 缓存按最近 1 天自动清理
- 朗读文本在本地做规则摘要，不额外调用模型
- 当前摘要规则控制在约 200 字内，优先抽取：
  - 结论
  - 结果
  - 验证
  - 下一步

### 2.8 刷新与缓存

需要做到：

- 线程切换更快
- 刷新时不要白屏
- 不能让缓存误导真实状态

实现方案：

- 只缓存历史内容，不缓存动态真相
- 刷新时允许先显示缓存消息
- 状态、队列、approval、可发送性仍以后端实时数据为准
- 如果缓存异常，直接退回安全加载链，避免空白页

原则：

```text
缓存内容，不缓存真相
```

## 3. 当前实现结果

截至当前版本，项目已经实现：

- Windows 托盘常驻
- 官方 thread / rollout 同步
- 浏览器与手机端查看线程
- 官方桌面 IPC 发送
- 手机公网二维码访问
- 本地队列与官方队列并存
- 自动下一步本地队列化
- 自动朗读与后端音频播放
- 附件上传到 Windows 本机并转为本机路径说明
- 刷新内容缓存与实时状态校正
- 按线程保存自动朗读 / 自动继续 / 连续次数上限

## 4. 关键设计取舍

### 4.1 为什么不直接写官方 SQLite

因为这样风险太大：

- 容易破坏官方状态一致性
- 容易和官方桌面内存态打架
- 不利于长期兼容

所以 Syncodex 的策略是：

- 读官方数据
- 发消息走官方支持的发送通道

### 4.2 为什么自动继续改成队列

因为旧方案太依赖完成事件和前端瞬时状态，容易漏触发。

改成队列以后：

- 行为更稳
- 更好调试
- 也更符合“继续下一步”本身就是一条任务的本质

### 4.3 为什么缓存只能做展示缓存

因为 Syncodex 是强状态页面。

如果缓存参与“是否空闲、是否可发送、是否有队列”的判断，就会造成误导。  
所以当前缓存只负责让页面更快显示已有内容，真实状态必须以后端实时同步覆盖。

## 5. 当前边界

目前仍然保留这些边界：

- 官方队列仍然只读
- 附件还不是官方原生附件协议，只是本机路径桥接
- 手机语音输入标点问题还没有完全解决
- 更复杂的项目级自动化模板还没有做
- 更细的语音参数配置还没有做
